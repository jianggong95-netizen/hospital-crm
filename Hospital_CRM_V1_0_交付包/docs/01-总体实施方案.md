# 医院CRM V1.0 总体实施方案

## 1. 项目目标

建设面向医院的客户关系管理与患者服务运营平台，覆盖客户建档、患者360、家庭账户、邀约分诊、预约、陪诊、上门服务、随访、客服、AI数字人、呼叫中心、短信、商保、投诉表扬、会员、收费结算和运营分析。

核心目标：
1. 建立统一客户身份和家庭关系模型。
2. 通过HIS适配层获取患者临床业务摘要，不直接耦合HIS数据库表。
3. 将陪诊、上门服务等增值服务形成可预约、可派单、可执行、可收费、可评价的闭环。
4. 建立人工客服与AI客服协同机制。
5. 所有订单、支付、退款、会员余额和次卡消费有可追溯流水。
6. 提供稳定、可版本化、可审计的标准API。

## 2. 已确认项目参数

| 参数 | 确认值 |
|---|---|
| HIS数据库 | Microsoft SQL Server |
| 部署 | 医院内网私有化 |
| 移动端 | 微信小程序 + H5 |
| 目标客户规模 | 约10,000人 |
| 收费 | CRM独立收费 |
| 商保 | API + 邮件 + 人工 |

## 3. 总体架构

### 3.1 逻辑分层
- 展示层：CRM管理端、患者小程序/H5、员工移动端。
- API接入层：API Gateway、认证、限流、版本控制、审计。
- 业务层：客户、家庭、预约、陪诊、上门、随访、客服、AI、呼叫、商保、投诉、会员、订单支付、报表。
- 集成层：HIS适配器、短信、呼叫中心、支付、商保、邮件。
- 数据层：PostgreSQL、Redis、RabbitMQ、MinIO、向量检索（可先用pgvector）。
- 运维层：日志、指标、链路追踪、备份、审计、告警。

### 3.2 部署原则
采用模块化单体起步，不在第一版拆成大量微服务。代码按领域模块分包，模块之间通过应用服务接口和领域事件交互。AI服务可独立为Python服务；后续有明确负载或团队边界时再拆分业务服务。

### 3.3 HIS与CRM数据库边界
- HIS SQL Server为临床业务数据权威源。
- CRM PostgreSQL为CRM客户运营、服务订单、会员、客服、随访任务和支付流水权威源。
- HIS连接账号默认只读；禁止CRM直接更新HIS临床表和收费表。
- HIS查询通过 `crm-his-adapter` 统一封装。
- 对HIS数据进行缓存时必须标记来源、获取时间、有效期和患者匹配置信度。
- 实际SQL视图、字段、主键、患者主索引、接口网络区域由医院现场调研确认。

## 5. 关键业务流程

### 5.1 客户与患者身份
1. 患者通过手机号、证件号或HIS患者标识查询。
2. 系统按配置的匹配规则给出候选结果。
3. 强匹配且唯一时可关联；多条候选或弱匹配时必须人工核验。
4. CRM生成内部 `customer_id`，保存HIS来源系统和外部患者ID映射。
5. 客户档案与HIS临床记录分开管理。
6. 客户合并采用申请、复核、执行、审计流程；禁止物理删除历史交易关联。

### 5.2 家庭账户
- 家庭账户与个人客户是不同实体。
- 一个家庭可关联多个个人客户；一个个人在同一时段默认只属于一个有效家庭，特殊情况通过关系规则扩展。
- 家庭管理员不自动拥有成员病历访问权。
- 代预约、代支付、共享套餐必须分别校验授权范围、有效期和撤销状态。
- 记录关系类型、授权人、被授权人、授权范围、有效期和撤销时间。

### 5.3 陪诊服务
客户选择服务项目、医院/院区、日期、时段和时长 → 查询可用陪诊师 → 创建待确认订单 → CRM支付或按配置先服务后支付 → 派单/接单 → 签到 → 开始计时 → 服务记录 → 完成确认 → 费用调整（如有）→ 结算 → 评价/投诉。
排班校验必须防止时间重叠，并支持交通缓冲、服务区域、技能、请假、临时停班和最大连续工作时长。
时长计费规则、最小起步时长、超时单位、取消费和退款规则由运营后台配置并保留版本。

### 5.4 上门服务
患者下单 → 服务范围及地址校验 → 医院审核（按项目配置）→ 资质与排班校验 → 派单 → 接单 → 服务前评估 → 上门签到 → 执行记录 → 患者确认 → 生成结算单 → 患者支付 → 评价。
涉及医疗行为的项目必须由医院审核服务目录、执行人员资质、服务规范和异常升级路径。CRM不代替医嘱、病历或医疗质量系统。

### 5.5 随访
配置随访分类、触发规则、模板、频次和责任组 → 事件或人工创建任务 → 分配人员/AI渠道 → 触达 → 记录结果 → 识别异常 → 转人工/临床团队 → 关闭任务。
AI不得自动诊断、修改治疗方案或处理紧急风险；高风险答案进入人工处理队列。

### 5.6 AI客服与人工转接
默认AI接待；患者第一次要求人工时提示确认并提供人工入口；第二次要求人工时自动进入人工队列。投诉、紧急、敏感、AI低置信度或明确要求人工的情况可直接转人工。人工接管必须携带完整会话上下文、患者授权范围和AI摘要。队列无人工时提供留言或回拨流程。

### 5.7 商保
登记保单 → 核验保障范围 → 询价/预授权 → 服务/就诊费用归集 → 材料收集 → 定损/理赔 → 补件或审核 → 赔付结果 → 医院应收对账。
分别保存医院应收、患者自付、保险预计赔付、保险实际到账，不将预计赔付视为收款。邮件模式需记录邮件Message-ID、附件哈希、发送/接收时间和人工操作人。

### 5.8 投诉表扬
登记 → 分类分级 → 受理 → 派发责任部门 → 调查 → 整改 → 反馈患者 → 复核 → 结案。重大投诉、超时和二次投诉需升级。客服“处理完成”不等同于结案。

## 6. 订单、支付与财务规则
- CRM收费独立于HIS收费；不得将CRM增值服务支付写入HIS收费表。
- 订单、订单项、支付单、支付流水、退款单、退款流水、对账单分表。
- 支付回调必须验签、幂等、校验金额和商户订单号。
- 每笔余额/积分/次卡变动必须写不可变账本；余额是账本汇总或受控缓存，不允许直接改余额字段代替流水。
- 支持全额/部分退款、撤销、支付超时、重复回调、支付成功但业务更新失败的补偿处理。
- 会员次卡消费需锁定权益并在订单取消/退款时按规则返还。
- 电子发票通过医院认可的第三方接口或财务系统对接。

## 7. 权限与数据安全
- RBAC角色权限 + 数据范围权限 + 字段级敏感数据权限。
- 采用最小权限原则；客服默认只能查看服务所需摘要。
- 家庭关系不构成病历访问授权。
- 身份证、手机号、地址等敏感字段加密或脱敏。
- 患者医疗健康信息按敏感个人信息管理，处理前确认合法处理基础、告知和单独同意等适用要求。
- 录音、聊天、AI对话、知识库上传均配置权限、留存期限和审计。
- 导出患者数据需审批、脱敏、水印和审计。
- 生产环境禁止使用真实患者数据做开发测试；使用脱敏或合成数据。
- 对接医院网络安全、等级保护、数据安全和个人信息保护制度。

## 8. 统计指标
- 客户新增数、有效客户数、重复客户率、家庭账户数。
- 邀约量、到院率、预约转化率、爽约率。
- 陪诊订单量、接单率、准时率、完成率、平均时长、评价分。
- 上门服务订单量、审核通过率、完成率、异常率。
- 随访触达率、完成率、异常转人工率。
- AI自助解决率、人工转接率、首次响应时间、平均处理时长。
- 投诉按期结案率、重复投诉率。
- 会员充值额、消费额、余额负债、次卡核销率。
- CRM服务收入、退款金额、支付成功率、商保应收及到账。

所有指标需定义统计口径、时间范围、数据权限和刷新频率。

## 9. 分期实施计划

建议按团队并行能力调整，以下是基线计划：
- P0 项目底座与安全：项目初始化、登录权限、组织、审计、配置、CI。
- P1 客户与HIS：客户、家庭、HIS适配、360、数据映射。
- P2 服务交易：预约、陪诊、上门服务、订单、支付、退款。
- P3 客户运营：邀约、分诊、随访、投诉表扬、消息。
- P4 智能客服：会话、人工工作台、知识库、AI、转人工、呼叫中心。
- P5 经营扩展：会员、商保、运营报表、绩效。
- P6 联调上线：安全测试、性能测试、备份恢复演练、用户验收、培训、灰度上线。

每期必须先完成业务流程、数据模型、API契约和验收用例，再编码。

## 10. 上线验收门槛
1. 关键业务流程有自动化测试。
2. HIS查询只读、字段映射有医院确认记录。
3. 患者身份匹配无静默错误合并。
4. 家庭授权不能越权查看医疗数据。
5. 支付回调幂等，重复回调不重复入账。
6. 余额和次卡账本可核对。
7. 订单状态机不允许非法跳转。
8. AI转人工会话上下文完整。
9. 商保预计金额和实际到账分离。
10. 备份恢复演练通过。
11. 关键日志可审计，敏感数据脱敏。
12. 压力测试达到医院确认的并发和响应目标。
