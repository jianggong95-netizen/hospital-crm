# 医院 CRM 运维手册（CRM-020 系统集成、上线与运维）

适用版本：V1.0（Spring Boot + PostgreSQL 16 + Docker Compose，私有化内网部署）
适用对象：医院信息科、系统集成商运维人员
文档位置：`ops/运维手册.md`

> 说明
> - 本文只描述可执行步骤。所有阈值、RPO/RTO、窗口时间均为**建议基线**，需医院信息科根据实际业务量确认后固化。
> - 告警规则编码、阈值最终以部署后 `GET /api/v1/ops/alerts/rules` 返回为准；本文第 6 章的规则表是 CRM-020 的基线口径。
> - 所有脚本、配置位于仓库 `ops/` 目录，不修改 `backend/`、`admin-web/`、`patient-mobile/` 与交付包文档。
> - 文中 PowerShell 示例默认在仓库根目录执行，PowerShell 5.1 兼容；bash 示例在 Linux 服务器执行。

## 1. 系统架构与进程/端口清单

### 1.1 逻辑架构

```
管理端浏览器 / 医护端 / 客服端 / 患者 H5、小程序
                    |
              HTTPS 反向代理 / API 网关 / WAF
                    |
        +-----------+-----------+
        |                       |
   crm-admin-web           crm-patient-web
        |                       |
        +-----------+-----------+
                    |
                 crm-api (Spring Boot, 8080)
        |            |            |            |
   PostgreSQL     Redis       RabbitMQ      MinIO
     (5432)      (6379)    (5672/15672)   (9000/9001)
                    |
              HIS SQL Server（只读，内网）
```

### 1.2 进程与端口

| 组件 | 进程/容器 | 默认端口 | 说明 |
|---|---|---|---|
| CRM API | `crm-api` / `java -jar crm-api.jar` | 8080 | 对外仅经反向代理暴露 HTTPS |
| 管理端 | `crm-admin-web` | 8081（宿主）→ 80（容器） | 静态资源 |
| 患者端 H5 | `crm-patient-web` | 8082（宿主）→ 80（容器） | 静态资源 |
| PostgreSQL | `postgres` | 5432 | 不对用户网段开放 |
| Redis | `redis` | 6379 | 仅应用网段 |
| RabbitMQ | `rabbitmq` | 5672 / 15672 | 15672 为管理台，限制来源 |
| MinIO | `minio` | 9000 / 9001 | 9001 为控制台，限制来源 |
| Prometheus（可选） | `crm-prometheus` | 9090 | `--profile ops` 启动 |
| Alertmanager（可选） | `crm-alertmanager` | 9093 | `--profile ops` 启动 |
| Grafana（可选） | `crm-grafana` | 3000 | `--profile ops` 启动 |

### 1.3 关键路径

| 路径 | 用途 |
|---|---|
| `backend/crm-boot/target/crm-api.jar` | 后端可执行包 |
| `run/` | 手工部署运行目录（jar、pid、日志） |
| `run/crm-api.pid` | 受管进程号，部署/回滚脚本依赖 |
| `run/crm-api.jar.prev` | 上一个可用 jar |
| `run/crm-api.jar.failed-<ts>` | 回滚时保留的失败 jar |
| `run/crm-api.log` | 应用标准输出日志 |

| `run/deploy-<ts>.log` | 部署日志 |
| `run/rollback-<ts>.log` | 回滚日志 |
| `backups/` | 默认备份目录 |

## 2. 环境与配置项

### 2.1 运行环境要求

- JDK 21（`java -version` 显示 21.x）。
- PostgreSQL 客户端工具 `pg_dump`、`pg_restore`、`psql`、`createdb`、`dropdb`，**主版本需与数据库一致（16.x）**。
- PowerShell 5.1（Windows Server 2016+）或 bash 4+（Linux）。
- `curl`（bash 脚本上报、健康检查需要）；Windows 使用 `Invoke-RestMethod`，不需要 curl。
- Docker Compose v2（容器化部署时）。

版本核对：

```powershell
java -version
pg_dump --version
$PSVersionTable.PSVersion
```

```bash
java -version
pg_dump --version
bash --version | head -n1
```

### 2.2 安全必填项（生产）

| 配置项 | 要求 | 备注 |
|---|---|---|
| `SPRING_PROFILES_ACTIVE` | `prod` | 关闭开发行为，日志切 JSON |
| `CRM_DB_URL` | `jdbc:postgresql://<db-host>:5432/<db>` | 不使用默认 dev 密码 |
| `CRM_DB_USERNAME` / `CRM_DB_PASSWORD` | 最小权限账号 + 强密码 | 密码不进 Git |
| `CRM_JWT_SIGNING_KEY` | ≥ 32 字节随机值 | 禁止使用 `dev-only-*` 默认值 |
| `CRM_DATA_ENCRYPTION_KEY` | Base64 编码的 32 字节 AES-256 密钥 | 需单独备份；更换前必须迁移历史密文 |
| `CRM_CORS_ALLOWED_ORIGINS` | 管理端、患者端真实域名 | 不使用 `*` |
| `CRM_BOOTSTRAP_ADMIN_PASSWORD` | 强密码 | 初始化完成后将 `CRM_BOOTSTRAP_ADMIN_ENABLED` 设为 `false` |
| `CRM_HIS_*` | 只读账号、批准视图 | 不把 HIS 数据库暴露到外网 |
| `CRM_HEALTH_SHOW_DETAILS` | `never` | 防止健康明细外泄 |
| Redis / RabbitMQ / MinIO 密码 | 独立强密码 | 不与数据库复用 |

生成密钥示例（Linux）：

```bash
# JWT 签名密钥（32 字节随机）
openssl rand -base64 32
# 数据加密密钥（32 字节随机后 Base64）
openssl rand -base64 32
```

Windows 可用 PowerShell 生成：

```powershell
$bytes = New-Object byte[] 32
[System.Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($bytes)
[Convert]::ToBase64String($bytes)
```

### 2.4 连接参数解析顺序（脚本）

备份、恢复、演练脚本按以下顺序取连接参数：

1. 命令行参数（仅备份脚本支持 `--database-url` / `--database`）。
2. `PGHOST` / `PGPORT` / `PGUSER` / `PGPASSWORD`。
3. `CRM_DB_URL` / `CRM_DB_NAME` / `CRM_DB_USERNAME` / `CRM_DB_PASSWORD`。
4. 默认值：`127.0.0.1:5432`、用户 `crm`、库 `crm`。

PowerShell 设置示例：

```powershell
$env:CRM_DB_URL = "jdbc:postgresql://10.10.20.31:5432/crm"
$env:CRM_DB_USERNAME = "crm"
$env:CRM_DB_PASSWORD = "<强密码>"
```

bash 设置示例：

```bash
export CRM_DB_URL='jdbc:postgresql://10.10.20.31:5432/crm'
export CRM_DB_USERNAME='crm'
export CRM_DB_PASSWORD='<强密码>'
```

> 生产环境不要把密码写入 shell 历史或脚本。建议使用受控环境文件（权限 600）、Windows 凭据管理器或医院密钥管理系统注入。

## 3. 首次部署步骤

### 3.1 顺序

1. 准备网络、域名、证书、反向代理。
2. 启动 PostgreSQL、Redis、RabbitMQ、MinIO。
3. 初始化数据库账号与库（如医院 DBA 未预先创建）。
4. 启动 `crm-api`，等待 Flyway 自动迁移完成。
5. 健康检查通过后启动管理端、患者端。
6. 修改初始管理员密码，关闭 bootstrap。
7. 执行首次全量备份并做一次恢复演练。

### 3.2 容器化启动

```bash
docker compose up -d postgres redis rabbitmq minio
docker compose up -d crm-api
docker compose ps
docker compose logs -f --tail=200 crm-api
```

Windows PowerShell 命令相同（Docker Compose v2 不区分 shell）。

### 3.3 手工初始化数据库

以 DBA 账号执行（示例，按医院规范调整）：

```bash
psql -h 10.10.20.31 -p 5432 -U postgres -c "CREATE ROLE crm LOGIN PASSWORD '<强密码>';"
psql -h 10.10.20.31 -p 5432 -U postgres -c "CREATE DATABASE crm OWNER crm ENCODING 'UTF8';"
```

```powershell
psql -h 10.10.20.31 -p 5432 -U postgres -c "CREATE ROLE crm LOGIN PASSWORD '<强密码>';"
psql -h 10.10.20.31 -p 5432 -U postgres -c "CREATE DATABASE crm OWNER crm ENCODING 'UTF8';"
```

Flyway 在应用启动时自动执行 `classpath:db/migration` 下的迁移，当前配置：

- `baseline-on-migrate: false`：不会对已有非空库自动建基线。
- `validate-on-migrate: true`：校验和必须一致，否则启动失败。

### 3.4 启动 API

容器方式见 3.2。手工 jar 方式：

```bash
java -XX:MaxRAMPercentage=75 -XX:+UseG1GC -jar backend/crm-boot/target/crm-api.jar \
  > run/crm-api.log 2>&1 &
echo $! > run/crm-api.pid
```

```powershell
New-Item -ItemType Directory -Force run | Out-Null
$p = Start-Process -FilePath "java" `
  -ArgumentList @("-XX:MaxRAMPercentage=75","-XX:+UseG1GC","-jar","backend/crm-boot/target/crm-api.jar") `
  -WorkingDirectory (Get-Location) `
  -RedirectStandardOutput "run/crm-api.log" -RedirectStandardError "run/crm-api-stderr.log" `
  -WindowStyle Hidden -PassThru
Set-Content -Path run/crm-api.pid -Value $p.Id -Encoding ASCII
```

生产建议使用 Windows 服务包装器（NSSM/WinSW）或 systemd 管理进程；`ops/deploy` 脚本适用于受控的手工发布窗口。

### 3.5 健康检查

```bash
curl -fsS http://127.0.0.1:8080/actuator/health
curl -fsS http://127.0.0.1:8080/actuator/health/readiness
curl -fsS http://127.0.0.1:8080/actuator/info
```

```powershell
Invoke-RestMethod http://127.0.0.1:8080/actuator/health
Invoke-RestMethod http://127.0.0.1:8080/actuator/health/readiness
Invoke-RestMethod http://127.0.0.1:8080/actuator/info
```

判定标准：HTTP 200 且返回体包含 `"status":"UP"`。

### 3.6 首次登录与账号安全

- 使用 `CRM_BOOTSTRAP_ADMIN_USERNAME` / `CRM_BOOTSTRAP_ADMIN_PASSWORD` 登录管理端。
- 立即修改密码，创建日常运维账号并分配最小权限。
- 将 `CRM_BOOTSTRAP_ADMIN_ENABLED=false` 后重启 API。
- 确认审计日志 `sys_audit_log` 有登录与初始化记录。

```

```

## 4. 版本升级步骤

### 4.1 升级前检查

- 已获取新版本 `crm-api.jar` 及发布说明，确认 Flyway 迁移方向（只允许向前）。
- 当前健康状态为 UP，`GET /api/v1/ops/jobs` 无异常堆积。
- 已完成一次当日备份，备份文件存在且 SHA-256 校验通过。
- 已确认回滚窗口与业务停机窗口（建议安排在门诊低峰）。
- 生产密钥、环境变量与旧版本一致（尤其 `CRM_DATA_ENCRYPTION_KEY`）。

### 4.2 使用部署脚本（推荐）

PowerShell：

```powershell
cd D:\hospital-crm
$env:SPRING_PROFILES_ACTIVE = "prod"
$env:CRM_DB_URL = "jdbc:postgresql://10.10.20.31:5432/crm"
$env:CRM_DB_USERNAME = "crm"
$env:CRM_DB_PASSWORD = "<强密码>"
$env:CRM_JWT_SIGNING_KEY = "<32字节以上密钥>"
$env:CRM_DATA_ENCRYPTION_KEY = "<Base64密钥>"

.\ops\deploy\deploy.ps1 `
  -JarPath backend\crm-boot\target\crm-api.jar `
  -AppDir D:\crm-run `
  -Port 8080 `
  -HealthUrl http://127.0.0.1:8080/actuator/health/readiness `
  -TimeoutSeconds 180
```

bash：

```bash
cd /opt/hospital-crm
export SPRING_PROFILES_ACTIVE=prod
export CRM_DB_URL='jdbc:postgresql://10.10.20.31:5432/crm'
export CRM_DB_USERNAME='crm'
export CRM_DB_PASSWORD='<强密码>'

bash ops/deploy/deploy.sh \
  --jar-path=backend/crm-boot/target/crm-api.jar \
  --app-dir=/opt/crm-run \
  --port=8080 \
  --health-url=http://127.0.0.1:8080/actuator/health/readiness \
  --timeout-seconds=180
```

脚本流程：

1. 预检：Java、jar、端口占用、磁盘 ≥ 2 GB、prod 密钥提醒。
2. 调用 `ops/pg/backup.ps1|.sh` 做数据库全量备份（`-SkipDbBackup` / `--skip-db-backup` 可跳过，不建议）。
3. 停止 `run/crm-api.pid` 对应的旧进程。
4. 旧 jar 复制为 `crm-api.jar.prev`。
5. 新 jar 复制为 `crm-api.jar`。
6. 启动并轮询 readiness，默认 120 秒。
7. 失败自动换回 `crm-api.jar.prev` 并重启，退出码 1。
8. 成功打印部署时间、日志路径与回滚命令，退出码 0。

部署日志：`<AppDir>/deploy-<yyyyMMdd_HHmmss>.log`。

### 4.3 升级后验证

```powershell
Invoke-RestMethod http://127.0.0.1:8080/actuator/health/readiness
Invoke-RestMethod http://127.0.0.1:8080/actuator/info
Select-String -Path D:\crm-run\crm-api.log -Pattern 'Started|Flyway|ERROR' -Tail 50
```

```bash
curl -fsS http://127.0.0.1:8080/actuator/health/readiness
curl -fsS http://127.0.0.1:8080/actuator/info
grep -E 'Started|Flyway|ERROR' /opt/crm-run/crm-api.log | tail -n 50
```

```bash
psql -h 10.10.20.31 -p 5432 -U crm -d crm -c \
  "SELECT installed_rank, version, description, success FROM flyway_schema_history ORDER BY installed_rank DESC LIMIT 5;"
```

```powershell
psql -h 10.10.20.31 -p 5432 -U crm -d crm -c "SELECT installed_rank, version, description, success FROM flyway_schema_history ORDER BY installed_rank DESC LIMIT 5;"
```

业务冒烟建议至少覆盖：登录、客户查询、订单/预约、患者 360、运维总览 `GET /api/v1/ops/overview`。

## 5. 回滚步骤

### 5.1 应用 jar 回滚（脚本）

PowerShell：

```powershell
.\ops\deploy\rollback.ps1 `
  -AppDir D:\crm-run `
  -Port 8080 `
  -HealthUrl http://127.0.0.1:8080/actuator/health/readiness
```

bash：

```bash
bash ops/deploy/rollback.sh \
  --app-dir=/opt/crm-run \
  --port=8080 \
  --health-url=http://127.0.0.1:8080/actuator/health/readiness
```

流程：

1. 停止 `crm-api.pid` 对应进程。
2. 若指定 `-RestoreBackupFile` / `--restore-backup-file`，先恢复数据库（需 `-Force`）。
3. 当前 jar 移为 `crm-api.jar.failed-<ts>`。
4. `crm-api.jar.prev` 恢复为 `crm-api.jar`。
5. 启动并轮询 readiness。
6. 无 `crm-api.jar.prev` 时明确报错并退出 1。

回滚日志：`<AppDir>/rollback-<yyyyMMdd_HHmmss>.log`。

### 5.2 回滚判定条件

满足任一条件执行回滚：

- readiness 连续 3 分钟非 UP，或部署脚本在超时内未通过健康检查。
- 5xx 比例持续 5 分钟 > 5%，且定位为新版本引入。
- 核心业务不可用：登录、客户查询、订单/预约主流程报错。
- Flyway 迁移失败且应用无法启动。
- 出现数据一致性异常或审计缺失。

### 5.3 数据库恢复注意事项

- **数据库恢复是破坏性操作**：`restore` 脚本对目标库执行 `pg_restore --clean --if-exists`，会删除同名对象。
- 当目标库等于 `CRM_DB_NAME`（默认 `crm`）时，必须显式 `-Force` / `--force`，否则脚本拒绝执行，这是防误操作保护。
- 恢复前停止应用写入、断开连接；恢复后核对 Flyway 版本、关键表行数与业务抽样。
- 旧版本 jar 只能搭配对应版本的数据库结构。若新版本已执行不可逆迁移，仅回滚 jar 可能导致启动失败，此时需同时恢复升级前备份。
- `CRM_DATA_ENCRYPTION_KEY` 必须与备份数据加密时使用的密钥一致，否则历史敏感字段无法解密。
- 恢复顺序：停应用 → 恢复数据库 → 回滚 jar → 启动 → 健康检查 → 业务验证。

PowerShell 数据库恢复回滚：

```powershell
.\ops\deploy\rollback.ps1 `
  -AppDir D:\crm-run `
  -RestoreBackupFile D:\crm-backups\crm_full_20261118_020000.dump
```

bash 数据库恢复回滚：

```bash
bash ops/deploy/rollback.sh \
  --app-dir=/opt/crm-run \
  --restore-backup-file=/data/crm-backups/crm_full_20261118_020000.dump
```

## 6. 监控与告警

### 6.1 指标清单

| 指标 | 类型 | 说明 |
|---|---|---|
| `up{job="crm-api"}` | Prometheus 内置 | 抓取目标存活 |
| `crm_api_requests_total{module,status}` | Counter | 接口请求数与状态码，5xx 比例口径 |
| `crm_api_request_duration_seconds{module}` | Histogram | 接口耗时，P95 口径（若后端导出 summary，则用 `quantile`） |
| `http_server_requests_seconds_*` | Actuator 默认 | Spring MVC 请求指标，可作辅助 |
| `jvm_memory_used_bytes` | Actuator 默认 | JVM 内存 |
| `jvm_gc_pause_seconds_*` | Actuator 默认 | GC 停顿 |
| `hikaricp_connections_active` | Actuator 默认 | 数据库连接池活跃数 |
| `crm_job_last_success_timestamp_seconds` | Gauge（CRM-020 自定义，待后端导出） | 任务最近成功时间 |
| `crm_backup_last_success_timestamp_seconds` | Gauge（CRM-020 自定义，待后端导出） | 备份最近成功时间 |

核对指标是否已导出：

```bash
curl -s http://127.0.0.1:8080/actuator/prometheus | grep -E 'crm_api_requests_total|crm_api_request_duration_seconds|crm_job_last_success|crm_backup_last_success'
```

```powershell
(Invoke-WebRequest -UseBasicParsing http://127.0.0.1:8080/actuator/prometheus).Content -split "`n" |
  Select-String 'crm_api_requests_total|crm_api_request_duration_seconds|crm_job_last_success|crm_backup_last_success'
```

### 6.2 应用内告警规则（8 条基线）

> 以下编码、阈值、窗口为 CRM-020 基线，部署后以 `GET /api/v1/ops/alerts/rules` 返回为准。阈值配置前缀 `crm.ops.alerts.*`，通过环境变量或 `application-prod.yml` 注入。

| # | 告警编码 | 名称 | 级别 | 触发条件 | 默认阈值 | 配置项 |
|---|---|---|---|---|---|---|
| 1 | `API_5XX_RATE` | 接口 5xx 比例过高 | HIGH | 统计窗口内 5xx/总请求 | 0.05（5%） | `crm.ops.alerts.api-5xx-rate-threshold` |

| 6 | `DB_POOL_EXHAUSTED` | 连接池接近耗尽 | HIGH | 活跃连接/最大连接 | 0.90 | `crm.ops.alerts.db-pool-used-ratio` |
| 7 | `HIS_ERROR_RATE` | HIS 调用失败率高 | HIGH | 统计窗口内失败率 | 0.20（20%） | `crm.ops.alerts.his-error-rate` |
| 8 | `OUTBOX_BACKLOG` | 消息积压 | MEDIUM | 待发送消息数 | 200 条 | `crm.ops.alerts.outbox-backlog-threshold` |

### 6.3 Prometheus / Alertmanager 使用

启动可选监控栈（不影响默认 `docker compose up`）：

```bash

docker compose --profile ops ps
```

访问：

- Prometheus：`http://<server>:9090`
- Alertmanager：`http://<server>:9093`
- Grafana：`http://<server>:3000`（首次登录 `admin` / `GRAFANA_ADMIN_PASSWORD`）

常用操作：

```bash
# 校验规则与配置
docker exec crm-prometheus promtool check config /etc/prometheus/prometheus.yml
docker exec crm-prometheus promtool check rules /etc/prometheus/alert-rules.yml
docker exec crm-alertmanager amtool check-config /etc/alertmanager/alertmanager.yml

# 重载
curl -X POST http://127.0.0.1:9090/-/reload
curl -X POST http://127.0.0.1:9093/-/reload

# 查看抓取目标
curl -s http://127.0.0.1:9090/api/v1/targets
```

Windows PowerShell 等价：

```powershell
docker exec crm-prometheus promtool check config /etc/prometheus/prometheus.yml
docker exec crm-prometheus promtool check rules /etc/prometheus/alert-rules.yml
docker exec crm-alertmanager amtool check-config /etc/alertmanager/alertmanager.yml
Invoke-RestMethod -Method Post http://127.0.0.1:9090/-/reload
Invoke-RestMethod -Method Post http://127.0.0.1:9093/-/reload
```

监控配置要点：

- `ops/monitoring/prometheus.yml` 抓取 `crm-api:8080/actuator/prometheus`。
- `ops/monitoring/alert-rules.yml` 含 6 条规则：`CrmApiDown`（critical，1m）、`CrmReadinessDown`（critical）、`CrmApi5xxRateHigh`（high，5m）、`CrmApiLatencyHigh`（medium，10m）、`CrmJobStale`（high）、`CrmBackupStale`（high）。
- `CrmReadinessDown` 依赖可选的 blackbox_exporter；未部署时由 `CrmApiDown` 兜底。
- `CrmJobStale` / `CrmBackupStale` 依赖 CRM-020 后端导出的自定义 gauge；未导出时由应用内 `JOB_STALE` / `BACKUP_STALE` 告警兜底。
- `ops/monitoring/alertmanager.yml` 中 webhook 与邮件地址是占位值，上线前必须替换。
- Grafana 首次使用需添加 Prometheus 数据源：`http://prometheus:9090`，再导入 JVM/HTTP 面板。

### 6.4 告警处理流程

1. 在管理端「运维中心 → 告警」查看 OPEN 告警。
2. 按 `dedupKey` 判断是否重复，重复告警只累加次数。
3. 处理后在告警详情执行确认（ack）；恢复后状态变为 RESOLVED。
4. 需要人工记录根因与处理时长的，写入医院运维工单。

## 8. 备份与恢复

### 8.1 策略与 RPO/RTO（建议值，需医院确认）

| 项目 | 建议基线 | 说明 |
|---|---|---|
| 全量备份 | 每日 1 次（低峰） | `pg_dump -Fc`，脚本自动计算 SHA-256 |
| 保留周期 | 14 天（`-RetentionDays`） | 按医院数据留存与等保要求调整 |
| 异地副本 | 每日同步至独立存储 | 与生产账号权限分离 |
| RPO | ≤ 24 小时（仅全量）；如需 ≤ 15 分钟需启用 WAL 归档 | 当前脚本只做全量逻辑备份 |
| RTO | ≤ 2 小时（以演练实测为准） | 含停应用、恢复、验证 |
| 演练频率 | 每月至少 1 次 | 使用 `drill` 脚本并留存 JSON 结果 |

> 当前交付脚本为**逻辑全量备份**，不包含 WAL 归档。若医院要求更低 RPO，需在 PostgreSQL 层启用 `archive_mode` + WAL 归档，并单独制定物理恢复流程；本手册不替代该项设计。

### 8.3 恢复

参数：

| 参数 | 必填 | 说明 |
|---|---|---|
| `-BackupFile` / `--backup-file` | 是 | `.dump` 文件 |
| `-TargetDatabase` / `--target-database` | 是 | 目标库 |
| `-CreateDatabase` / `--create-database` | 否 | 目标库不存在时创建 |
| `-Force` / `--force` | 条件 | 目标库等于 `CRM_DB_NAME` 时必须显式提供 |

PowerShell：

```powershell
# 恢复到临时库验证
.\ops\pg\restore.ps1 `
  -BackupFile D:\crm-backups\crm_full_20261118_020000.dump `
  -TargetDatabase crm_restore_check `
  -CreateDatabase

# 恢复到生产库（停应用后执行，必须 -Force）
.\ops\pg\restore.ps1 `
  -BackupFile D:\crm-backups\crm_full_20261118_020000.dump `
  -TargetDatabase crm -CreateDatabase -Force
```

bash：

```bash
bash ops/pg/restore.sh \
  --backup-file=/data/crm-backups/crm_full_20261118_020000.dump \
  --target-database=crm_restore_check --create-database

bash ops/pg/restore.sh \
  --backup-file=/data/crm-backups/crm_full_20261118_020000.dump \

```

校验内容：

- `.sha256` 存在时逐字节比对 SHA-256；不一致立即失败。

### 8.4 恢复演练（验收重点）

参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `-SourceDatabase` / `--source-database` | `CRM_DB_NAME` 或 `crm` | 源库 |
| `-DrillDatabase` / `--drill-database` | `crm_restore_drill_yyyyMMddHHmmss` | 演练库 |
| `-BackupDir` / `--backup-dir` | `./backups` | 备份目录 |
| `-ApiBaseUrl` / `-ApiToken` | 空 | 上报备份与演练结果 |
| `-KeepDrillDatabase` / `--keep-drill-database` | 否 | 保留演练库排障 |

PowerShell：

```powershell
.\ops\pg\drill.ps1 `
  -BackupDir D:\crm-backups `
  -ApiBaseUrl http://127.0.0.1:8080 `
  -ApiToken $token
```

bash：

```bash
bash ops/pg/drill.sh \
  --backup-dir=/data/crm-backups \
  --api-base-url=http://127.0.0.1:8080 \
  --api-token="$TOKEN"
```

执行步骤与判定：

1. 调用备份脚本生成新备份（`-SkipReport`，避免重复上报）。
2. 创建演练库。
3. 调用恢复脚本恢复备份。
4. 对比源库与演练库：
   - `crm_customer`、`crm_order`、`crm_appointment`、`crm_metric_definition`、`sys_audit_log` 行数完全一致。
   - `flyway_schema_history` 成功迁移数量与最新 version 完全一致。
5. 全部一致输出 `PASS`，否则 `FAIL` 并给出具体原因，退出码 1。
6. 结果写入 `<BackupDir>/drill-result-<yyyyMMdd_HHmmss>.json`。
7. 提供 API 参数时：先 `POST /api/v1/ops/backups` 上报备份，取得 `data.id` 后 `POST /api/v1/ops/backups/{id}/verify`，请求体 `{"restoreVerified":true|false,"message":"..."}`。
8. 默认删除演练库；`-KeepDrillDatabase` 保留。

判定标准（验收）：

- `DRILL_STATUS=PASS`。
- 5 张关键表行数差值为 0。
- Flyway 最新版本一致且迁移数量一致。
- 后台备份记录 `restoreVerified=true`。

演练失败时保留现场：

```powershell
.\ops\pg\drill.ps1 -BackupDir D:\crm-backups -KeepDrillDatabase
```

```bash
bash ops/pg/drill.sh --backup-dir=/data/crm-backups --keep-drill-database
```

## 10. 常见故障处置

### 10.1 数据库连接失败

现象：readiness DOWN，日志 `Connection refused` / `Connection reset` / `HikariPool` 超时。

```powershell
Test-NetConnection 10.10.20.31 -Port 5432
psql -h 10.10.20.31 -p 5432 -U crm -d crm -c "SELECT 1;"
docker compose ps postgres
docker compose logs --tail=100 postgres
```

```bash
pg_isready -h 10.10.20.31 -p 5432 -U crm
psql -h 10.10.20.31 -p 5432 -U crm -d crm -c "SELECT 1;"
docker compose ps postgres
docker compose logs --tail=100 postgres
```

处置：确认数据库进程、端口、防火墙、账号密码、连接数上限；必要时重启 postgres 容器；应用恢复后复查连接池。

### 10.2 Flyway 校验失败

现象：启动失败，日志包含 `Validate failed`、`checksum mismatch`、`Migration Vxx failed`。

```powershell
psql -h 10.10.20.31 -p 5432 -U crm -d crm -c "SELECT installed_rank,version,description,checksum,success FROM flyway_schema_history ORDER BY installed_rank DESC LIMIT 10;"
```

```bash
psql -h 10.10.20.31 -p 5432 -U crm -d crm -c "SELECT installed_rank,version,description,checksum,success FROM flyway_schema_history ORDER BY installed_rank DESC LIMIT 10;"
```

处置：

- 禁止直接修改已执行迁移文件；校验和不一致需由开发确认。
- 迁移失败且事务已回滚：修复脚本后重试，或恢复升级前备份。
- 不要在生产直接执行 `flyway repair`；必须经变更审批并确认影响。
- 回滚应用 jar 前确认数据库结构是否已向前迁移。

### 10.3 定时任务停滞

现象：业务数据未按时生成，`JOB_STALE` 告警，`GET /api/v1/ops/jobs` 最近成功时间过旧。

```bash
curl -fsS -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8080/api/v1/ops/jobs
curl -fsS -H "Authorization: Bearer $TOKEN" "http://127.0.0.1:8080/api/v1/ops/jobs/<jobCode>/runs?limit=20"
```

```powershell
$headers = @{ Authorization = "Bearer $token" }
Invoke-RestMethod -Headers $headers http://127.0.0.1:8080/api/v1/ops/jobs
Invoke-RestMethod -Headers $headers "http://127.0.0.1:8080/api/v1/ops/jobs/<jobCode>/runs?limit=20"
```

处置：查看任务日志与最近失败原因；确认是否被数据库锁、外部接口超时或线程池占满；修复后等待下一周期或按流程手工触发。

### 10.4 备份失败

排查顺序：

1. `pg_dump` 是否在 PATH 且版本与数据库一致。
2. `PGPASSWORD` / `CRM_DB_PASSWORD` 是否正确，账号是否有读权限。
3. 备份目录是否存在、磁盘是否已满、是否有写权限。
4. 数据库中是否有长事务阻塞 `pg_dump`。
5. 查看 `.meta.json` 是否生成、脚本退出码。

```powershell
Get-ChildItem D:\crm-backups | Sort-Object LastWriteTime -Descending | Select-Object -First 6
pg_dump --version
Get-PSDrive D | Select-Object Free
```

```bash
ls -lt /data/crm-backups | head -n 6
pg_dump --version
df -h /data
```

处置：修复后立即补做一次全量备份并执行 `drill` 验证；不要在未确认新备份可用前删除旧备份。

### 10.5 接口 5xx

1. 从响应头取 `X-Trace-Id`。
2. 在 `crm-api.log` / `crm-api-error.log` 检索该 traceId。
3. 查看 `crm-api-error.log` 最近异常堆栈。
4. 检查数据库连接池、HIS 超时、Redis/RabbitMQ 可用性。
5. 若新版本上线后突增且无法快速定位，按第 5 章回滚。

```powershell
Select-String -Path D:\crm-run\crm-api-error.log -Pattern '<traceId>' -Context 2,10
```

```bash
grep -n -C 10 '<traceId>' /opt/crm-run/crm-api-error.log
```

### 10.6 磁盘满

```powershell
Get-PSDrive | Where-Object { $_.Used -ne $null } | Select-Object Name,Used,Free
Get-ChildItem D:\crm-run\logs -Recurse | Sort-Object Length -Descending | Select-Object -First 10 FullName,Length
```

```bash
df -h
du -xh /opt/crm-run/logs /data/crm-backups | sort -h | tail -n 10
```

处置：

- 清理已按保留策略过期的滚动日志（`.gz`），不要删除当前 `crm-api.log`。
- 将备份目录迁移到独立磁盘或异地存储。
- 检查是否有异常日志风暴（如循环报错），先止血再清理。
- 清理后确认应用可写日志、数据库可写 WAL。

### 11.2 回滚判定条件

出现以下任一情况，立即停止发布并回滚：

- 部署后 3 分钟内 readiness 未通过，或自动回滚已触发但需人工确认。
- 新版本导致登录、客户查询、订单/预约等核心流程不可用。
- 5xx 比例连续 5 分钟超过 5%，且排除基础设施因素。
- Flyway 迁移失败导致应用无法启动，或出现不可逆结构变更。
- 出现数据错误、敏感数据泄露、审计记录缺失等安全事件。
- 医院业务部门确认无法在可接受时间内恢复。

回滚执行顺序：

1. 通知业务与信息科，记录开始时间。
2. 停止应用（或由回滚脚本停止）。
3. 如数据库结构已变化，恢复升级前备份（必须 `-Force`，确认目标库）。
4. 执行 `rollback` 脚本换回 `crm-api.jar.prev`。
5. 健康检查与核心业务冒烟。
6. 保留失败 jar、日志、`drill-result` 与备份，提交问题分析。
